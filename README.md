# kaspi-price-feed

Открытая часть монолита **BuyShark**: Python-пакет для подготовки, загрузки и
сверки XML-прайс-листов Kaspi. Можно использовать как основу своего Kaspi SaaS.
Лицензия **AGPL-3.0-only** с условием сохранения атрибуции из `NOTICE`.
Автор: **Venius24**, исходный проект: **BuyShark**.

Проект создавался с помощью AI. Я открываю эту часть, чтобы другим разработчикам
не пришлось заново собирать базовый механизм прайс-фида.

## Что внутри

- XML `kaspi_catalog`: цена с настраиваемым cityId, остатки, доступность, экранирование SKU.
- Полный снимок каталога: отказ при оборванной пагинации, дублях, отсутствующих
  данных и подозрительном уменьшении количества активных офферов.
- План изменений с диффом и обратной проверкой состава готового XML.
- Названия и бренды из выгрузки Kaspi или ранее принятого файла.
- Загрузка multipart, проверка квоты FILE, ожидание нового файла в финальном статусе.
- Архив отправленного XML, метаданные, gzip-копии и ротация точек восстановления.
- Сверка с каталогом после загрузки: пропавшие карточки, расхождения цен/остатков,
  объяснение изменений во время обработки и остановка фида при потерях.
- Проверка артикулов, которые не переживают нормализацию при приёме файла.

Это библиотека. В неё не входят интерфейс, демпинг-движок, биллинг,
планировщик, база BuyShark и автоматический вход в кабинет Kaspi.
Каталог, авторизацию HTTP и очередь изменений подключает ваше приложение.
У пакета нет обязательных внешних зависимостей.

## Быстрый запуск

Python 3.10 или новее:

```bash
git clone https://github.com/Venius24/kaspi-price-feed.git
cd kaspi-price-feed
python -m pip install -e '.[dev]'
python examples/dry_run.py
python -m pytest -q
```

Пример использует десять вымышленных товаров, печатает изменения и сохраняет
`demo-feed.xml`. Он не обращается к сети и не загружает файл в Kaspi.

## Подключение к своему SaaS

```python
from pathlib import Path
from kaspi_price_feed import Integrations, use_integrations, build_feed_plan

adapters = Integrations(
    catalog=load_full_catalog,
    merchant_id=resolve_merchant_id,
    request=authenticated_mc_request,
    cached_products=load_previous_catalog,
    pending_intents=load_pending_changes,
    data_dir=Path("/var/lib/my-saas/kaspi-feeds"),
)

with use_integrations(adapters):
    plan = build_feed_plan(token, store_id)
    print(plan.total, plan.changed_offers, plan.blockers)
```

Функции в примере реализуются в вашем приложении:

| Адаптер | Контракт |
| --- | --- |
| `catalog(token, *, store_id, strict)` | Полный список активных **и архивных** офферов; при сбое пагинации бросает `AssortmentTruncated(reason, collected)`, а не возвращает часть данных. |
| `merchant_id(token, *, store_id)` | Настоящий merchant ID соответствующего магазина. |
| `request(method, url, *, store_id, **kwargs)` | Авторизованный MC-запрос для магазина; принимает `headers`, `params`, `files`, `timeout` и возвращает объект с `status_code`, `text`, `content`, `json()`. Совместим с ответом `requests`. |
| `cached_products(store_id)` | Предыдущий каталог для независимой проверки размера; необязательный. |
| `pending_intents(store_id)` | `{merchantSku: {price, stock, available, reason, priority}}`; без адаптера очередь пустая. Можно передать `intents` прямо в `build_feed_plan`. |
| `moved_after_snapshot(store_id, snapshot_at)` | SKU, изменённые вашим приложением после снимка, включая уже отправленные JSON-изменения. |
| `acknowledge_intents(store_id, declared, snapshot_at)` | Транзакционно закрывает только намерения, существовавшие до снимка и совпадающие с доставленными значениями. Возвращает `(settled, kept_queued)`. Без адаптера очередь не изменяется. |
| `notify(store_id, category, message, **kwargs)` | Необязательный синхронный или асинхронный обработчик тревог. Без него тревоги пишутся в лог. |

Оффер каталога: `merchantSku`, `price_num`, `stock`, `available` (или
`status="Активен"`), необязательные `name`, `brand`, `point_store_id`.
Сериализатор записывает один склад и один cityId на оффер, `preOrder="0"`.
Формат поля наличия на складе и параметров XML описан в `xml_feed.py`.
Идентичность товара в фиде берётся из XML Kaspi: display-название бренда из
каталога не заменяет его slug в прайс-листе.

Адаптеры ограничены контекстом `use_integrations`. Асинхронные задачи сохраняют
свой контекст; при запуске работы в отдельном потоке используйте
`contextvars.copy_context()` либо открывайте контекст внутри этого потока.
Каталог и HTTP-функции синхронные; не вызывайте длительное ожидание загрузки
непосредственно в event loop.

## Загрузка и сверка

**XML объявляет весь каталог, а не только изменённые товары.** Пропущенный
оффер может быть снят с продажи. Сериализатор сам по себе не доказывает полноту
входных данных: используйте снимок, план и проверки перед загрузкой.

Отправка по умолчанию выключена. Для реальной загрузки нужны одновременно:
`XML_FEED_UPLOAD_ENABLED=1`, `confirm`, совпадающий с merchant ID плана,
свежий план, проверенные поля идентичности и отсутствие блокеров. Изменения
дополнительно разрешаются `allow_changes=True`.

```python
from pathlib import Path
from kaspi_price_feed import send_plan, settle_file

with use_integrations(adapters):
    plan = build_feed_plan(token, store_id)
    verdict = send_plan(
        plan, store_id, plan.snapshot.merchant_id,
        confirm=plan.snapshot.merchant_id, allow_changes=True,
    )
    if verdict.archive_path is None:
        raise RuntimeError("XML не сохранился: требуется ручная проверка каталога")
    report = settle_file(
        store_id, Path(verdict.archive_path), verdict, token=token,
    )
    if report.needs_attention:
        print(report.summary())
```

`FLUSHED` означает завершённый разбор файла, а не доказательство правильности
каталога. После отправки выполняйте `settle_file` со свежим каталогом.
Для автоматического цикла проверяйте `feed_state.is_enabled(store_id)` перед
каждой загрузкой: `send_plan` — низкоуровневая явная операция и сама не проверяет
рубильник фонового воркера. Организуйте блокировку на магазин, чтобы два писателя
не отправляли файлы одновременно. После таймаута не повторяйте отправку вслепую.

Данные сохраняются в `Integrations.data_dir`, переменной
`KASPI_PRICE_FEED_DATA_DIR` или `.kaspi-price-feed` в текущем каталоге.
Используйте постоянный закрытый каталог данных и стабильные безопасные `store_id`.

## Ограничения

- MC endpoints — интеграция с кабинетом Kaspi, их контракт может меняться.
- Наследуемые пороги: минимум 5 активных офферов в снимке, усадка более 10%
  вызывает отказ, максимальный возраст плана — 300 секунд.
- Отсутствующая независимая ACTIVE-выгрузка отмечается предупреждением.
  Если она доступна, обнаруженные пропуски блокируют отправку. Перед первым
  включением проверьте полноту своего адаптера и актуальность выгрузки.
- Состояние хранится в файлах, без межпроцессной синхронизации. Для нескольких
  воркеров требуется блокировка вашего приложения.
- Очередь намерений, её транзакции и уведомления принадлежат вашему приложению;
  их реализация не входит в пакет.
